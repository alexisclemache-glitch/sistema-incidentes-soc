Defensa del proyecto

Sistema de gestión de incidentes SOC/CSIRT

Aplicación web con persistencia PostgreSQL, API REST y control de acceso por roles.

Repositorio: alexisclemache-glitch/sistema-incidentes-soc

URL pública: completar después de verificar el despliegue de Render.

Notas del presentador

Indicar que la URL solo se entrega como operativa después de validar /salud en el Web Service de Render.

01 · Objetivo

Registrar y dar seguimiento a incidentes

  • Centralizar el registro en una base relacional persistente.
  • Proporcionar operaciones de crear, consultar, actualizar y eliminar.
  • Separar los registros por usuario y permitir supervisión administrativa.
Notas del presentador

Describir el problema como necesidad de trazabilidad y control de acceso; evitar atribuir capacidades de un SIEM que el prototipo no implementa.

02 · Arquitectura

Capas pequeñas y responsabilidades claras

Navegador
HTML · CSS · JS→ HTTPS / JSON →Express
REST · JWT · validación→ TLS →PostgreSQL
usuarios · incidentes
Notas del presentador

En Render, Express puede servir frontend y API en el mismo origen. Los controladores validan y los modelos ejecutan consultas parametrizadas.

03 · Flujo demostrable

De inicio de sesión a cambio persistido

1. Acceso

Registro de analista o login de administrador.

2. Operación

Crear un incidente con título, severidad y descripción.

3. Seguimiento

Editar estado, consultar lista y eliminar el registro de prueba.

Notas del presentador

Demostrar con información ficticia. Abrir /salud primero. Mostrar edición y cierre de sesión. Si no hay despliegue, hacer la demo local solo si la base local está preparada.

04 · Seguridad

Identidad, propiedad y transporte

Autenticación

Contraseñas bcrypt; JWT Bearer con expiración de ocho horas.

Autorización

Analista consulta lo propio; administrador consulta todos. El propietario se aplica en SQL.

Protecciones

Validación, consultas parametrizadas, CORS, Helmet, HTTPS/HSTS y TLS para PostgreSQL en Render.

Notas del presentador

El registro público no asigna rol ADMIN. Los secretos viven en el entorno del servidor, nunca en el JavaScript público.

05 · Persistencia

CRUD autenticado sobre PostgreSQL

  • GET /api/incidentes — listar según rol.
  • POST /api/incidentes — crear para la cuenta autenticada.
  • PUT /api/incidentes/:id — actualizar campos permitidos.
  • DELETE /api/incidentes/:id — eliminar con autorización.
Notas del presentador

El esquema se crea con CREATE TABLE IF NOT EXISTS. No existe todavía un sistema de migraciones versionadas.

06 · Calidad

Pruebas y señales operativas

  • 15 pruebas automatizadas con Node.js Test Runner y Supertest.
  • Cubren salud, CORS, autenticación, roles, validación y CRUD.
  • /salud comprueba PostgreSQL y responde 200 o 503.
  • Morgan genera logs de solicitudes en entornos distintos de test.
Notas del presentador

Las consultas se sustituyen en pruebas: no es una integración real con PostgreSQL ni una prueba E2E del navegador.

07 · Despliegue y límites

Estado transparente del proyecto

  • Repositorio versionado en GitHub; Blueprint de Render define servicio y base.
  • Render necesita JWT_SECRET, ADMIN_EMAIL y ADMIN_PASSWORD configurados.
  • URL pública: pendiente de despliegue exitoso y verificación de /salud.
  • Mejoras: rate limiting, recuperación de cuenta, auditoría, migraciones y pruebas E2E.
Notas del presentador

No afirmar que la app está online si Render no muestra el Web Service como Live. La base de datos sola no constituye una URL de aplicación.
